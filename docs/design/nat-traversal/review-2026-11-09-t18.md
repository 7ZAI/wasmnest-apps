### [x] H1. WAN 注册表的 UI 语义与后端判定相反（安全语义误导）

- **严重度**：High ｜ **类别**：bug / security
- **文件**：
  - `servers/net-config/desktop/src/components/WanPolicyCard.vue:24,28,68-86`
  - `servers/net-config/desktop/src/composables/useWanPolicy.ts:52-61`
  - `servers/net-config/desktop/src/components/NetConfigView.vue:169-174,333-337`
  - 后端口径：`apps/bedcode/desktop/rust/src/relay_center.rs:170-178`
- **问题**：后端 `allow_wan_for` 对「未登记 / 缺字段」返回 **`true`（允许外网）**；前端却把 `row.entry?.allowWan` 为 `null/undefined` 一律渲染成「禁止」、不计入 `allowedWanCount`，并触发「当前没有业务允许走外网」提示。`toggle` 对未登记行取 `!(entry?.allowWan ?? false)`，第一次点击只会写入 `true`（原本就生效），用户无法从当前显示状态直接关闭。
- **影响**：用户看到所有业务「禁止外网」，实际 BedCode 仍会建立中继预留——暴露面与 UI 相反；`net-config-wan-off-hint` 也是假提示。`netConfigView.test.ts` R7（约 380-424 行）把这个错误语义写成了期望；E2E 只断言 `data-allowed ∈ {true,false}`，抓不到。
- **建议**：先统一语义再测。任选其一：
  1. UI/`useWanPolicy` 把未登记视为「允许」（与 `spec` §「未显式设置时 true」一致）；
  2. 后端默认改为 `false`（更 fail-closed），同步 T18 文案、spec 与该用例。

  同时补「未登记业务的显示 / 首次切换」行为用例。
- **验证**：`servers/net-config` 的 `test:run`；人工检查空 `network.wanPolicy` + 已配置 relay 时页面显示与实际 `session.tunnel.prepare` 的 `allowWan` 一致。

## 3. Medium

### [x] M1. 中心回执缺 `configured` 字段时被当成「用户主动清空」，跳过缓存兜底

- **严重度**：Medium ｜ **类别**：bug（fail-visible）
- **文件**：`apps/bedcode/desktop/rust/src/relay_center.rs:116-128`
- **问题**：`payload.get("configured").and_then(Value::as_bool).unwrap_or(false)`：中心返回非对象、缺字段或类型错误时都落到 `configured:false`，直接返回「未配置」，既不报错也不回落到本地缓存——与模块文档「结构不对 = 中心回执损坏，不静默当空」矛盾。
- **建议**：

  ```rust
  let configured = payload
      .get("configured")
      .and_then(Value::as_bool)
      .ok_or_else(|| "network centre reply missing configured".to_string())?;
  ```

  补 `FakeCenter::new(Ok(json!({})))` 的缓存兜底用例。
- **验证**：`cargo test --manifest-path apps/bedcode/desktop/rust/Cargo.toml --lib relay_center`。

### [x] M2. `wanPolicyError` 后端有、前端从未消费；策略读取失败时 fail-open 且原因不可见

- **严重度**：Medium ｜ **类别**：bug / security 可观测性
- **文件**：
  - `apps/bedcode/desktop/rust/src/relay_center.rs:186-200`（返回 `wanPolicyError`）
  - `apps/bedcode/desktop/src/composables/useTunnelStatus.ts:32-44`
  - `apps/bedcode/desktop/src/components/RelayMovedSection.vue:95-105`
- **问题**：`allow_wan_for` 在策略读取失败时按默认 `true` 继续（有意 fail-open），但 `wanPolicyError` 在两侧 `RelayConfigView` 接口里都没有声明、没有 UI 展示；`device_face` 虽把 `wan_error` 拼进 `relayError`，该字段在 QR 前端类型里同样没有消费者。结果：中心不可用时，用户显式关闭的外网会重新放开，页面上却看不到「策略读不到」的原因——票面要求「失败时原因必须可见」。

### [x] M3. 每次 activate 都尝试迁移；中心异常时阻塞启动，prepare 故障路径可能重复等两次中心

- **严重度**：Medium ｜ **类别**：性能 / 生命周期
- **文件**：
  - `apps/bedcode/desktop/rust/src/lib.rs:1186-1206`
  - `apps/bedcode/desktop/rust/src/relay_center.rs:205-250`（`CALL_TIMEOUT_MS = 5000`）
  - `apps/bedcode/desktop/src/composables/useTunnelStatus.ts:96-107` + `apps/bedcode/desktop/rust/src/lib.rs:1600-1645`
- **问题**：迁移成功后本地键按设计保留为缓存，因此**之后每次启动**都会再走一次 `relay_adopt`；中心异常时最坏阻塞 5s。另 `session.relay.config` 失败后前端仍会调 `session.tunnel.prepare` 且不带参数，后端会再解析一次中心（第二次 5s 超时），设备页 / 准备页在中心挂起时可能等 ~10s。
- **建议**：`migration_status` 为 `adopted/skipped` 时跳过重复 adopt（或改首次使用时懒迁移）；让 `relay-config` 与策略合并为一次读取，或让 `prepare` 接受「本次已失败」不再二次请求。
- **验证**：native 用例锁「已是 adopted → 不再调用 adopt」；中心超时场景的页面 loading 时长。
