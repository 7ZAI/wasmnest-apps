## 1. 阻断项（先修，不修则 T09/T10 不可能通过）

### R01 — T09 扫码后没有走隧道，仍直连原设备

- [ ] **修复**
- **严重度**：阻断
- **规格锚点**：spec §4.9「新版移动始终走 tunnel」；T09「扫码路径先建隧道再连回环代理」；不变量 3/8。
- **证据**：
  - `apps/bedcode/mobile/src/host/components/DevicesSection.vue:1222-1228`：构造了 `target`（`proxy.address` + `proxy.port`），但下一行是 `ctrl.connectDevice(device, …)`；`device` 来自 QR 原始 `host:port`。
  - 结果：`openTunnel` 建的 `127.0.0.1` 代理没有被任何连接使用；WAN 场景直接拨原地址必失败，LAN 场景绕过 `caller=peer` 对等面。
  - `onQrConnect` 的 catch 才会 `closeTunnel`；成功路径会遗留一个空转的代理句柄。
- **修复建议**：
  1. `onQrConnect` 中把 `ctrl.connectDevice(device, …)` 改为 `ctrl.connectDevice(target, …)`（`proxy` 为 `null` 时 `target === device`，旧载荷行为不变）。
  2. 确认 Step 1 后 `waitForConnected` 使用代理地址；`authenticateWithQr` 继续走宿主当前连接。
  3. 补一条组件测试：QR v2 带 `peer` → `connectDevice` 收到的 `address === '127.0.0.1'` 且 `port === proxy.port`；QR v1 → 仍收到原始 `host/port`。
- **验证**：`apps/bedcode/mobile` 的 `test:run` 里新增用例；再跑 T09 既有 681 条不回归。

### R02 — `tunnel.connect` 回执 `address` 含端口，移动宿主会拼成双端口

- [ ] **修复**
- **严重度**：阻断
- **规格锚点**：spec §4.4 客户端返回 `{ addr:"127.0.0.1", port:<ephemeral>, handle }`；T05「本地代理 listener 只绑 127.0.0.1」。
- **证据**：
  - `wasmnest-server-peer-net/src/tunnel/manager.rs:583`：`address: addr.to_string()`，值为 `"127.0.0.1:5000"`，同时返回 `port: 5000`。
  - `ConnectEntry` 的注释（同文件 `:229-235`）写的是「本地回环代理地址（只可能是 127.0.0.1）」，与实现不一致。
  - 移动宿主按 `ws://{address}:{port}` 建 URL（`src-tauri/src/commands/connection.rs:191-202`），会得到 `127.0.0.1:5000:5000`。
- **修复建议**：
  1. `address: addr.ip().to_string()`（只回 `127.0.0.1`），`port: addr.port()` 保持独立。
  2. 修 `ConnectEntry` 注释。
  3. 补回执形状锁：`address` 必须是不含 `:` 的 IP 字面量（IPv6 场景另议，但当前只绑 IPv4 loopback）。
- **验证**：`wasmnest-server-peer-net` 的 tunnel 单测 + 一条 `connect` 回执 JSON 断言；修完 R01 后跑移动端 `tryWan` 路径。

## 2. 高优先级（安全/生命周期，建议与阻断项同批）

### R03 — `allowWan=false` 时只要候选含 relay，LAN 也被整体拒绝

- [ ] **修复**
- **严重度**：高
- **规格锚点**：spec §4.9「`allowWan=false` 时只关外网，不自动切 wan」；T06「LAN 入口不受影响」；不变量 9。
- **证据**：`manager.rs:463`：`let wan = !wan_addrs.is_empty(); if wan { if !config.allow_wan { return Err(wan-disabled) } }`。QR v2 的 `peer.addrs` 固定是 LAN+relay；手机设置关掉远程访问后，`connect` 在尝试 LAN 前就失败。
- **修复建议**：
  1. `allowWan=false` 时**过滤掉** `wan_addrs`，保留 `lan_addrs` 继续 `plan_mode` / `dial`；只有在“没有 LAN 候选且需要 WAN”时才返回 `wan-disabled`。
  2. `relay_addrs` 未配置时同理：不要把整个 `connect` 打死。
  3. 补用例：候选 `[LAN, relay]` + `allowWan=false` → 成功走 LAN；`[relay]` + `allowWan=false` → `wan-disabled`。
- **验证**：`wasmnest-server-peer-net` tunnel 单测；移动 T09 `configure` + `connect` 组合用例。

### R04 — 认证失败被误报成网络不可达；混合候选会误切 WAN

- [ ] **修复**
- **严重度**：高
- **规格锚点**：spec §4.9 判据表「认证失败 / 未匹配 / Noise 失败 → 保持当前模式，报安全错误」；不变量 9「只有明确判据能触发 lan→wan」。
- **证据**：
  - WAN 分支 `manager.rs:516-523`：`engine.dial_classified` 失败后不看 `failure.kind`，一律 `CODE_RELAY_UNREACHABLE` + `mark_wan_unavailable(RelayUnavailable)`；`NotAdmitted` / `NodeIdMismatch` 也被当成中继不可达。
  - LAN 分支 `manager.rs:490-505`：`LanFailure::Auth` 也走 `lan-unreachable`，用户看到「内网不可达」而不是安全错误。
  - `classify_p2p_dial`（`manager.rs:1249-1256`）对 `DialAllFailed` 调 `classify_dial_text(detail)`；`detail` 是 `p2p-engine/src/engine.rs:375-377` 拼接的逐候选文本。只要一条是 `no route to host`，另一条是 timeout，整体就被判 `Unreachable` → 自动切 WAN。
- **修复建议**：
  1. 让引擎 / peer-net 回**结构化逐候选成因**（`Vec<DialFailure>`），不要在拼接字符串上做子串匹配。
  2. `judge_after_lan_failure` 只在**全部**候选都是 `Unreachable` 时返回 `SwitchWan`；任一 `Auth` 优先返回安全错误；混合 timeout/refused/unreachable 保守保持 LAN。
  3. WAN 拨号失败按 `failure.kind` 映射：`Auth` → `not-matched` / 安全错误；`Relay`/`Unreachable` → `relay-unreachable`；不要把认证失败标成 `wan-unavailable`。
  4. 补锁：`NotAdmitted` 的 LAN/WAN 失败都不切 relay；`[EHOSTUNREACH, timeout]` 不切 WAN；`[EHOSTUNREACH, EHOSTUNREACH]` 才切。
- **验证**：`wasmnest-server-peer-net` 判据测试 + `wasmnest-p2p-engine` 拨号错误测试。

### R05 — `stop` 不清 expose 规则、不清票据、不杀在飞入站流

- [ ] **修复**
- **严重度**：高（安全/生命周期）
- **规格锚点**：spec §4.4「关闭即释放」；T06「1→0 释放 reservation / 清空全部状态」；不变量 4/8。
- **证据**：
  - `manager.rs:311-336`：清 `state.rules/configs/modes`、`policy.clear_peer_face()`、`registry.clear_all()`，但**没有**清 `TunnelPolicy` 里的 expose 规则；**没有**清 `TicketIssuer`；`inbound_task.abort()` 只停接收循环。
  - `run_inbound_loop` 在 `manager.rs:919` `spawn` 的 `TunnelServer::handle_stream` 任务没有被跟踪；`stop` 不 abort 它们。
  - 后果：`stop → start` 后 `policy` 仍能 admit 旧 tcp 端口；旧票据在 TTL 内仍有效；在飞配对流的 registry 条目被 `clear_all` 清掉，pairing 标记消失但 pipe 继续。
  - `TunnelManager::expose` 在 `stop` 后再次调用时，`policy.expose` 会返回旧 rule id（`policy.rs:200-209`），manager 把 owner 改成新调用方，旧 `allowed_peers`/label 静默保留。
- **修复建议**：
  1. `stop` 中按 `policy.rules()` 逐条 `unexpose`，或重建 `TunnelPolicy`（注意 `server` 持有 Arc）。
  2. `TicketIssuer` 增加 `clear()` / 按端口撤销；`stop` 与 `unexpose` 都要清对应票据。
  3. 跟踪在飞 `TunnelServer` 任务（`JoinSet` 或 `HashMap<AbortHandle>`），`stop` 时 abort / 等待；至少保证配对流和业务流被关闭。
  4. 补回归：`expose → stop → start` 后旧端口 `port-not-exposed`；旧票据 `ticket-expired`；stop 后在飞 WS 被关闭。
- **验证**：`wasmnest-server-peer-net` manager/ticket 测试。

### R06 — 配对窗口可开 `kind=tcp` 业务端口；票据消费顺序不符 spec

- [ ] **修复**
- **严重度**：高/中
- **规格锚点**：T05「配对窗口只放行配对端点；tunnel 只到配对端点；配对窗口连接不得复用于业务」；spec §4.4 校验顺序（matched → allowedPeers → port/kind → ticket → quota）。
- **证据**：
  - `policy.rs:234-305`：未匹配 peer + `ticket_valid` → `pairing=true`，随后 `kind=Tcp` 仍返回 `Backend::Loopback(hello.port)`；没有“配对态只允许 http 配对端点”的限制。
  - `server.rs:84-112`：先 `tickets.consume(ticket, hello.port, …)`，再 `policy.admit` 查规则/端口/管理端口。端口填错会先烧掉一次性票据，然后才报 `port-not-exposed`。
  - 另外 `allowed_peers` 非空时，配对票据也受该列表约束（`policy.rs:276-283`）；新设备不在列表时无法配对，需确认这是否为预期（T07 用空列表，暂不触发）。
- **修复建议**：
  1. 配对态只允许 `kind=http`（或显式配置的 pairing kind）；`kind=tcp` 直接拒绝。
  2. 把票据消费移到“规则/端口/kind 已通过、且确实需要 pairing”之后；失败路径不要消耗票据（或在非票据错误时回滚）。
  3. 明确 `allowed_peers` 是否适用于配对窗口；建议配对窗口不受 `allowed_peers` 限制，或单独定义 `pairing_allowed_peers`。
- **验证**：`policy`/`server` 单测：配对 tcp 拒绝；错误端口不烧票据；配对窗口只放行 `/api/auth/*`。

### R07 — `matched` 只认传输信任，没有应用配对输入（需裁定）

- [ ] **确认口径 / 修复**
- **严重度**：高（取决于裁定）
- **规格锚点**：T05「peer 已匹配（应用配对 + 传输信任两层同时成立）」；不变量 8；spec §9.2#2 默认「按设备 + 宿主全局信任现状」。
- **证据**：`manager.rs:903` 的 `matched = engine.trust_contains(node_id).await`；`TunnelStreamContext`（`server.rs:40-50`）没有应用配对字段。当前 auth-center 配对成功写的是同一张 peer 信任表（T07/T08）；file-transfer 首连确认也写这张表。因此“file-transfer 已确认”会让 bedcode 隧道被判 matched。
- **修复建议（二选一，先定口径）**：
  - **A. 全局信任口径**：确认 §9.2#2 就是“传输信任 = 已匹配”，在 `TunnelStreamContext`/文档中写明；补一条测试锁说明 file-transfer 首连与 bedcode 隧道共享信任。优点是实现简单；风险是跨应用权限扩大。
  - **B. 两层口径**：增加 `app_pairing` 端口（auth-center 记录 / `PairingRecord`）注入 `TunnelStreamContext`；`matched = transport_trust && app_pairing`。需要新增端口与调用链，T05/T06/T07 重新验收。
- **验证**：若选 B，补“仅传输信任、无应用配对 → `not-matched`”；若选 A，补文档 + 回归锁。

## 3. 中低优先级（P2，按顺序收）

### R08 — 入站接收循环退出后不会重启

- [ ] **修复**
- **规格锚点**：T05/T06 入站 `/wasmnest/tunnel/1` 接收生命周期。
- **证据**：`manager.rs:896-901` `next_inbound()` 返回 `None` 就 `break`；`ensure_running`（`:770-781`）只看 `inbound_task.is_none()`，不检查任务已结束。节点重启 / `accept_streams` 短暂失败后，入站隧道永久失效直到完整 stop/start。
- **修复**：`inbound_task` 改存 `JoinHandle` 或带 `is_finished()` 的句柄；循环退出时置空并记录原因；`ensure_running` 重新拉起；`next_inbound` 的错误与“无流”区分开。

### R09 — TUNNEL 未在 `start_with_protocols` 预注册

- [ ] **修复**
- **规格锚点**：T05「tunnel 流接收器接线：`start_with_protocols` 注册 `TUNNEL` 并显式 `require_admitted = false`」。
- **证据**：`base/transport.rs:643-649` 的 `protocols` 列表只有 TRUST_STATUS / TRANSFER / SHARED_DIR / SESSION；`manager.rs:1081-1084` 用懒 `accept_streams(TUNNEL, false)`。节点已监听、接收器未注册的窗口内，对端 `open_stream` 会失败。
- **修复**：把 `TUNNEL` 加入启动协议表；`accept_streams` 的 `require_admitted=false` 语义保留；manager 复用 `start_with_protocols` 返回的接收器，而不是二次注册。

### R10 — `kind=tcp` 的 `expose` 也强制启动 peer face

- [ ] **修复**
- **规格锚点**：spec §4.4：只有 `kind=http` 的后端恒为对等面；`kind=tcp` 只需回环。
- **证据**：`manager.rs:358-370` 两个分支都 `ensure_peer_face()`。无对等面 starter 的无头 / 移动宿主无法暴露 tcp 端口。
- **修复**：只在 `kind=Http`（或需要配对票据）时启动 peer face；tcp 规则只要求节点 + 入站接收器。

### R11 — reservation 计数不跟 relay 地址变更

- [ ] **修复**
- **规格锚点**：T06 单一引用计数 + `configure` 全量替换 relay 配置；T02 `reserve_relay` 幂等替换。
- **证据**：`manager.rs:828-887` 只算 `desired` 与 `reserved`；`need_reserve = desired > 0 && !state.reserved`。运行中修改 relay 地址，旧 reservation 继续用，直到计数归零。
- **修复**：记录当前 reservation 使用的地址集合；地址变化且 `desired>0` 时调用 `reserve_relay(新地址)` 替换；失败保留旧 reservation 并显性告警。

### R12 — `status.node.addrs` 在 relay `Connecting/Lost` 时也追加 circuit

- [ ] **修复**
- **规格锚点**：T06 第三轮「relay 预留生效时追加 `<relay>/p2p-circuit/p2p/<self>`」；T08 `peer.addrs` 必须可拨。
- **证据**：`manager.rs:1148` 只看 `relay_status().relay_addr` 是否为 `Some`；`p2p-engine/src/engine.rs:759-775` 在 `Connecting/Lost` 也保留 endpoint。QR 会带不可用的 relay 候选。
- **修复**：只有 `relay_status().state == RelayState::Reserved` 时才追加 circuit；`Lost/Connecting` 只给 LAN，状态里单独给 relay 状态。

### R13 — 域名 relay 未走宿主 `lookup_host`

- [ ] **修复**
- **规格锚点**：T02「relay 域名地址由宿主层 `tokio::net::lookup_host` 解析成 IP 再拼 multiaddr」。
- **证据**：`resolve_relay_addr` 只在 `p2p-engine/src/relay.rs:256` 定义与测试中使用；`TunnelConfig::parse_relay_addrs`（`manager.rs:210-222`）只做 `Multiaddr` 解析；`RelayEndpoint::parse`（`relay.rs:148`）对 DNS 组件显性拒绝。域名 relay 配置会在 reserve 时失败。
- **修复**：`configure` / `reserve_relay` 前对每条 relay 地址调用 `resolve_relay_addr`，持久化/状态里保留原始输入与解析结果；解析失败显性报错并点名地址。

### R14 — peer face listener API 未自证 loopback

- [ ] **修复**
- **规格锚点**：T03 / 不变量 1「peer face 只绑 127.0.0.1」。
- **证据**：`server-core/src/app.rs:155-177` `serve_peer_face_on` 接受调用方传入的 `std::net::TcpListener`，不校验 `local_addr().ip().is_loopback()`；`serve_on` 直接 `listen(listener)`。当前桌面 starter 正确，但机制层可被误用。
- **修复**：`serve_peer_face_on` / `serve_on` 在 `face.is_peer()` 时校验 listener 的本地地址必须是 loopback；非 loopback 返回 `AddrNotAvailable` 或显性错误。

### R15 — 其余小项（可合并一个 PR）

- [ ] `policy.rs:251` + `manager.rs:905-910`：并发配额 off-by-one（自增后 `>= max` 实际只允许 `max-1`）；改为先判后增或 `>`。
- [ ] `policy.rs:176-209`：`expose` 幂等命中时不更新 `allowed_peers/label`；改为更新 ACL（或要求先 unexpose）。
- [ ] `manager.rs:413-429`：`unexpose` 不撤销该端口票据；与 R05 一起补 `TicketIssuer::revoke_port`。
- [ ] `pipe.rs:104-125`：WS 升级只检查首次 8KiB `read`；改为累积到 `\r\n\r\n`（带上限）再判定，避免分片/大 header 的 WS 被 60s 空闲回收。
- [ ] `manager.rs:546-556`：本地代理任务退出只 `warn`；补 `tunnel-error` / 状态回落，避免状态栏显示已连接。
- [ ] `TunnelManager::close` 的 `recount` 失败路径会先移除 handle 再返回错误；确认 lease 不会因此泄漏，必要时先回滚状态。
