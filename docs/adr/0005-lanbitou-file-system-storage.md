# 烂笔头（lanbitou）笔记存储：文件系统优先，不使用数据库

**状态**：accepted（2026-11-02）

## 背景与问题

烂笔头（lanbitou）是轻量级桌面记事本应用，需要持久化用户笔记。存储方案有两种选择：

1. **文件系统**：每个笔记存储为独立的 `.md` 文件，元数据（时间戳）用同目录 `index.json` 持久化
2. **SQLite 数据库**：使用宿主提供的 `host-plugin-database` 能力，笔记内容和元数据存入关系表

关键约束：
- 产品定位是"纯文本记事本"，强调可移植性和开放性
- 笔记数量预期较少（单用户 < 1000 篇）
- 需要支持 Markdown 格式，且用户可能用其他编辑器打开笔记文件
- 应用重启后需要恢复工作上下文（最后打开的笔记、光标位置等）

## 决定

**采用文件系统存储**，具体方案：

1. **笔记文件**：`~/.wasmnest/lanbitou/notes/<uuid>.md`，UTF-8 编码的纯文本
2. **工作上下文**：`~/.wasmnest/lanbitou/context.json`，记录当前编辑状态
3. **设置**：`~/.wasmnest/lanbitou/settings.json`，记录用户偏好
4. **持久化索引**：`~/.wasmnest/lanbitou/index.json` 只存 `(id, createdAt, updatedAt)`；
   标题始终由正文首行派生。列表时扫描 `notes/` 并与索引合并——外部复制进来的文件
   自动入索引，被外部删除的文件自动剔除；索引损坏时整份回退为空索引，列表扫描目录
   重建（时间戳回退为当前时间），不阻塞启动

5. **临时记事（默认文档）**：`~/.wasmnest/lanbitou/notes/scratch.md`，id 固定为
   `scratch`。激活时自愈（缺失即建空文档），列表固定置顶，不可重命名 / 删除
6. **归档**：`~/.wasmnest/lanbitou/archives/<起日>_<今日>.md`。归档 = 把临时记事的
   全部内容**剪切**进新文件（正文原样、不重排），源文档随后清空；起日取正文里最早的
   ISO 日期（时间分隔符里的 `{{date}}`），正文没有日期则回退到文档创建日。同名归档
   追加 `_2`/`_3`，不覆盖旧记录。归档在应用内只读打开，不做二次编辑
   （日期由前端按本地时区给：wasm 侧只有 Unix 毫秒，拿不到本地日）

**不使用数据库**，即使 `host-plugin-database` 能力已可用。

## 理由

### 选择文件系统的优势

1. **可移植性**：用户可直接用 VSCode、Typora、系统记事本等任何编辑器打开笔记文件，无需导出
2. **Git 友好**：笔记文件可纳入版本控制，支持 diff、blame、历史回溯
3. **符合产品定位**："纯文本记事本"的核心价值是简单、开放、无锁定
4. **调试友好**：文件内容直观可见，无需数据库客户端查询
5. **备份简单**：复制目录即完成备份，无需导出工具

### 不使用数据库的理由

1. **过度设计**：笔记数量少，文件扫描性能可接受（< 1000 文件，启动时一次性扫描 < 100ms）
2. **增加复杂度**：需要数据库迁移、版本管理、查询接口，与"轻量"定位冲突
3. **降低可移植性**：数据库文件无法直接用其他工具打开，违背"纯文本"精神
4. **调试困难**：需要数据库客户端查看内容，增加用户和开发者的认知负担

### 性能权衡

- **列表读取**：扫描 `notes/` 目录并对每个文件读正文（标题取首行），1000 篇量级可接受
- **排序 / 搜索**：时间戳来自 `index.json`，排序不依赖文件系统 mtime；搜索在 Rust 命令面（`lanbitou.search-notes`）做大小写不敏感匹配，前端只发查询串
- **并发写入**：单用户场景无并发问题；索引与正文分两次写，异常中断后靠扫描重建索引

## 后果

### 正面

- 用户笔记文件可直接用其他编辑器打开，无供应商锁定
- 备份和同步只需复制目录（可用 Syncthing、iCloud、Dropbox 等）
- 代码实现简单，无数据库抽象层
- 符合 WasmNest "纯文本优先"的设计哲学

### 负面

- 需要自己实现索引构建和一致性维护（但逻辑简单，列表时扫描合并即可）
- 无法使用 SQL 查询（但索引 + 前端过滤已足够）
- 大量笔记时列表读取可能变慢（但产品定位是"轻量"，预期不会超过 1000 篇）

### 风险与缓解

- **索引不一致**：文件被外部修改时，索引中的时间戳可能过期
  - 缓解：列表按目录扫描合并；外部新增文件补索引，外部删除文件剔除索引
- **文件损坏**：写入中断可能导致文件不完整
  - 缓解：索引可重建；正文损坏需用户从备份 / 版本控制恢复（不做静默覆盖）
- **性能瓶颈**：笔记数量超过预期时列表变慢
  - 缓解：索引已持久化，后续可改为按需读取正文 / 增量标题缓存

## 替代方案

### 方案 A：SQLite 数据库

- 笔记内容存入 `notes` 表（id, title, content, createdAt, updatedAt）
- 工作上下文存入 `settings` 表（key-value）
- 优点：查询灵活、事务性强、性能可预测
- 缺点：不可移植、需要数据库管理、违背"纯文本"精神
- 结论：**拒绝**，与产品定位冲突

### 方案 B：混合方案（文件 + 索引数据库）

- 笔记内容存文件，元数据索引存 SQLite
- 优点：兼顾可移植性和查询性能
- 缺点：需要维护两套存储的一致性，复杂度增加
- 结论：**拒绝**，过度设计

### 方案 C：JSON 文件索引

- 笔记内容存 `.md` 文件，索引存 `index.json`
- 优点：启动时直接读索引文件，排序时间戳稳定
- 缺点：需要维护索引文件与文件系统的一致性
- 结论：**已采纳**（见决定 4）——索引只存时间戳，标题由正文派生；列表时扫描目录合并，外部增删文件可被拾取
