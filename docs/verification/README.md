# 端到端功能验证模板（按 app）

> **本目录是功能验收模板与报告口径，不替代自动化 E2E。**
> 自动化用例的写法和运行方式仍以 `docs/E2E.md` 与 `e2e/specs/` 为准；模板补的是
> 「真实网络 / 真实对端 / 真实 API Key / 跨端链路」等自动化覆盖不到的部分，以及发布前
> 需要归档的功能结论。

---

## 1. 这套模板解决什么

| 层         | 回答的问题                                           | 产物                                |
| ---------- | ---------------------------------------------------- | ----------------------------------- |
| 单元测试   | 纯逻辑 / composable / 组件逻辑对不对                 | `pnpm run test:run`                 |
| 自动化 E2E | 真实宿主里界面能不能点、状态会不会翻转               | `node scripts/e2e.mjs --app <slug>` |
| **本模板** | **功能是否完整可用、边界是否诚实、真实链路是否打通** | 一份可归档的验证报告                |

每个 app 一份模板，包含四块：

1. **功能清单**：用户可见能力、端、边界与前置，作为覆盖范围的真源；
2. **验证步骤**：按功能域分组，每步一个 checkbox，写清「做什么 → 期望看见什么」；
3. **已知缺口**：文案 / 命令存在但界面未接通、或明确未实现的能力，**不纳入通过判据**，
   避免把「点不到」误判成「刚测坏」；
4. **维护触发**：功能变更时同批更新模板。

**建议使用时机**：每个 app 发版 tag 前、跨端协议 / 权限门变更后、交互面大改后的合并前；
日常小改动仍以单测 + 自动化 E2E 为准，不必每次跑完整模板。

## 3. 怎么生成一份验证报告

### 3.1 命名与位置

```text
docs/verification/reports/<YYYY-MM-DD>-<slug>-v<应用版本>.md
```

示例：`docs/verification/reports/2026-10-26-file-transfer-v0.0.1.md`。
应用版本取该端 `plugin.json` 的 `version`；双端一致时只写一个版本。

### 3.2 步骤

1. **锁定被测对象**：记录应用版本、提交（`git rev-parse HEAD`）、宿主版本
   （`host-runtime.lock.json` 的 `hostRuntime`）、端与设备。
2. **跑自动化基线**：按 `docs/E2E.md` 跑该 app 的 E2E；结果先记入报告头，
   再执行模板中的人工步骤（`【手动】` / `【真机】` / `【需 Key】` / `【双端】`）。
   自动化红时不要继续用人工步骤「盖过去」。
3. **生成报告**：先复制 [`_report-template.md`](_report-template.md) 作为报告头，
   再把对应 `<slug>.md` 的「§2 验证准备」与「§3 验证步骤」追加到报告 §6。
4. **逐项执行**：严格按编号顺序；每步完成后立即标记并写证据。
5. **收尾**：填报告头、汇总数量、写结论；失败项登记 issue（`docs/agents/issue-tracker.md`）。

### 3.3 标记口径（完成打钩、未完成打叉）

| 状态            | 写法       | 说明                                               |
| --------------- | ---------- | -------------------------------------------------- |
| 通过            | `- [x] ✅` | 实际观察与期望一致；有证据                         |
| 未通过          | `- [ ] ❌` | 实际与期望不符；行尾写原因 + issue 链接            |
| 未完成 / 不适用 | `- [ ] ⏭`  | 该步没跑，或该端无此能力；**必须写原因**，不得留空 |

模板文件本身保持全部 `- [ ]`（不带 ✅/❌/⏭）；标记只发生在报告副本里。
**未标记的步骤 = 未完成**，不能计入通过。时间受限时可先跑标注「核心」的功能域；
报告必须逐项写明未执行项，不能因「只跑了核心」直接判通过。

报告片段示例：

```markdown
- [x] ✅ S-01-01 打开应用并落地概览（证据：截图 / E2E 用例通过）
- [ ] ❌ S-02-03 环境检测重试后仍失败（原因：…；issue #123）
- [ ] ⏭ S-09-01 移动端步骤（本次无真机，未执行）
```

### 3.4 结论判据

- **通过**：全部步骤为 `[x] ✅`，或仅有书面说明的 `[ ] ⏭`（不适用，且不影响核心链路）；
- **不通过**：存在任一 `[ ] ❌`；
- **未完成**：不存在 ❌，但仍有未执行的必测步骤。

核心链路（模板中标注「核心」的功能域）出现 ❌ 时，结论必须为**不通过**，不得以
「其他都通过」抵消。

## 4. 执行环境与证据要求

- **真实宿主**：桌面验证用 `node scripts/e2e.mjs --app <slug>` 同源的宿主运行时；
  人工目验也优先用它，而不是 SDK dev-shell / devMock（mock 壳不代表真实权限门）。
- **版本对齐**：宿主版本必须满足 `host-runtime.lock.json`；不匹配时先同步 lock，
  否则结果不可归档。
- **移动端**：用 debug APK + 真机（见 `docs/E2E.md` §11）；`e2e-mobile.mjs` 会自动起
  1423 dev server 并做 `adb reverse`（已在跑则复用）。模拟器 / dev-shell 只能做预检。
- **证据**：失败项至少附截图或日志路径；自动化项附命令与退出码；不许只写「试过了」。
- **凭据**：API Key / 配对码 / 设备指纹等敏感信息**不得**写入报告；凭据只记长度或末四位。
- **环境隔离**：涉及真实用户数据的步骤（清空历史、轮换密钥、撤销信任、卸载 CLI、清空统计）
  必须先确认测试环境专用，不得在用户日常数据上执行。

## 5. 维护纪律

- **功能变更 = 模板变更**：新增 / 删除 / 改名用户可见能力时，同批更新功能清单与步骤；
  改动 `data-testid` 时同步更新模板中的自动化引用与 `e2e/pages/`。
- **已知缺口要诚实**：已实现后从「已知缺口」移入功能清单并补步骤；确认不做的写明裁定。
- **不复制规范**：测试纪律、锚点命名、E2E 运行方式引用 `docs/E2E.md` 与
  `../wasmnest/docs/public/testing.md`，本目录只写「验什么、怎么判」。
- **模板版本**：每份模板头部记 `模板版本` 与日期；结构性调整时递增并写明变更。
